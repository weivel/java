`com.weivel.host`, held to the core's `docs/contract/host.md`, whose classes are listed in [its source doc](../../source/src/main/java/com/weivel/host/README.md). `Host` registers plugins written in Java from a manifest value and an `Entry`, the plugin's `CompletionStage<?> activate(PluginContext)`, which may also implement `Deactivating`; a throw, a `null` stage or a stage completing exceptionally is a failure. `Entries.load` makes an entry by its class name from the caller's class loader, and `Host.loadEntry` from a JAR in a class loader of the host's own, whose parent is the loader of `Entry`; the host never assumes a name. `activate` asks the core for the plan and starts each plugin of its order in that order on the calling thread, never waiting for an activate, and answers the plan at once with each plugin's outcome as a stage: active, quarantined, refused, released or failed. An outcome carries the core's refusal that decided it: a refused one the refusal of its open, and one quarantined because the core refused its verification that refusal; a quarantine for a reason of the host's, a failed activate among them, carries none. Where no dispatch runs it starts them as one step of a dispatch, so what an activate's own calls queue is dispatched once every activate of the plan has been called; where another thread is dispatching, it starts them as calls made while that dispatch runs, and their events join the end of that thread's queue. Either way an activate that settles before it returns is verified, and quarantined if the core refuses, in the same hold of the layer lock, before the next plugin is started; a failed one is quarantined with a reason saying so, any NUL character in the failure's text written as `\0`, since the reason is the host's own text and not a caller's mistake. `verify` verifies a plugin as a settled activate is verified and answers its outcome by the same rule, a quarantine the core's refusal caused carrying that refusal. An activate runs as the dispatcher, so one that blocks on an event another thread causes deadlocks: an activate that must wait answers a stage and completes it later. `release` calls the deactivate while the plugin is whole, releases it in the core, and ends its entries and forgets it only once that release's events are dispatched, as a step behind them inside a dispatch. `registerHostService` offers a service of the host's own under `WEIVEL_HOST`, which an activation plan counts as provided. `destroy` answers one `CompletionStage<DestroyResult>`: it releases every plugin opened, the last opened first, waits for the opens and settlings under way, then disarms the timer and destroys the core, and every other call answers `Destroyed` from the moment it is called. `ledger` answers the core's ledger, where a plugin quarantined for a refused verification shows the core's refusal, and `HostOptions.withTimerObserver` hears each move of the host's timer, armed or disarmed. `close` frees what the host holds, the class loaders it opened among them, and is refused until the destroy has finished. A host its caller gives no scheduler arms the language's own timer rather than none: it makes one with `Schedulers.system()` and closes it when it is closed, so a want that needs the time is never the caller's mistake. The host also loads C libraries as host services, as the two files below describe.

- [libraries.md](libraries.md) - loading a C library as host services: bytes services, definitions, when the binary closes, and what a call allocates
- [descriptions.md](descriptions.md) - a definition bound from its description, so a Java plugin calls a C library that ships no Java source
